# Original external playlist import binding

Required Root construction, in the same original music entry:

```kotlin
val external = DesktopOriginalExternalPlaylistBinding(
    sameSettingsContext,
    sameDesktopAudioRepository,
) { originalRootFactory.captureRequest(sameAssembly) }
```

Supply this object as `DesktopOriginalMusicUiPlatform.externalPlaylist`.
Use the existing DesktopAudioRepository passed to lyrics/music. Its public
`externalPlaylistCalls` is an alias of the existing bounded public lyrics client;
it has no Bilibili cookie jar, new client, queue, preference document or cache.
The original QQ headers and NetEase public device cookie remain in the original
repository requests. Every call captures the actual caller Job before IO, and
the cancellation handle remains installed through response body parsing/closure.

`captureRequest` requires the same initialized native session but does not require
an accepted source, successful video load, nonzero CID or active playback. Do not
capture once for a whole page, replace the existing Repository, or silently retag
an old request to a successor account. A matching batch retains one Binding in its
coroutine context; nested checkpoint saves reuse it. The original checkpoint key
is global settings, as upstream defines it, rather than account-partitioned data.

The complete original ExternalPlaylistImportDialog's async state publications use
the required music `commitUi` hook. Inside its existing short Root admission it
must call `DesktopSubscriptionWriteAdmission.checkCurrentRequestOrOriginal()` in
addition to caller/entry/account checks. The original progress callback carries
that same batch receipt. Checkpoint saves, matching delay, network calls, parsing,
temporary file IO and native waits stay outside this UI gate. Root's same context
must be pinned to the entry/account lifetime for publications after a fetch has
returned. Existing saved/dismiss callbacks also retain Root's entry lifetime.

The original external schema remains solely generated by the existing music
producer. The added domain selects its original parsing/encryption/matching and
checkpoint methods. The existing search producer selects the complete original
video search, WBI signing fallback and error policy, borrowing the canonical
SearchPageInfo and SearchLoadPolicy. No source identity or dependency was added.

Actual78 complete desktop classes and 46 zero-override fixture assertions pass.
The fixture uses fake Search/Nav APIs, real loopback HTTP (including a body read
blocked before cancellation), and the real original settings Store. Installed
product class origins are unique. This does not accept the full captured Binding
under a real account, remote QQ/NetEase/Bilibili endpoints, native window, complete
Root mounting or the delivered EXE. Those remain joint Root/runtime work.

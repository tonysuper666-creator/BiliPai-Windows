**What changed against the synthesized draft** (details in section 13):

1. The player work is ordered so the user sees a visible player improvement in Release 1, before any carrier-dependent work. Release 1 needs no carrier.
2. The input-delivery probe V0 is the first deliverable. It cites the hardware failure already recorded for the offline player, runs three probe arms plus a keyboard matrix plus a GPU/CPU/memory budget, and carries a designed contingency (V0b, extending the mpv native input bindings). The draft's "AWT-listener fallback" is withdrawn, because a repo comment says that channel cannot work.
3. The dock over video is original liquid glass by default (tier 1) whenever the original app's own gate allows it. The scrim-plus-fallback look (tier 2) is used only where the original also falls back.
4. Panel open/close, cinema and splitter changes snap. The 160 ms width animation is removed, because it would resize the native slot every frame.
5. The hidden-state progress line moves to its own tiny window, so the full-surface carrier repaints nothing while idle. Hidden controls are unmounted, so they cannot swallow clicks.
6. Reserved-file, Gradle and CI bookkeeping is corrected, and the five pin test classes that the cloud plan does not run are called out.
7. Settings fixtures, NVIDIA trigger, quality gating, click latency, keyboard focus and several shortcut conventions are corrected.
8. The Home vendored-page baseline (pointer flag, scrollbar, hover, right-click) is promoted. The window-maturity items (bounds persistence, title) are scheduled.
9. The classic-layout promise in the user's mockup is addressed explicitly (decision D7).
10. The scope is cut into an MVP, a fast-follow and a later list, with a compile after every slice and a slice size cap.
11. Golden tables were recomputed in a scratch script. The feed table was confirmed. Two player rows were wrong at widths under 1280 and are corrected in section 4.3.

## 1. Goal and principles

### 1.1 Goal

Turn the shipped "vendored Android UI in a desktop window" into a mature Windows desktop app. Keep the original liquid-glass material look by default. Keep every feature. The user said on 2026-10-18 that the app is "half phone, half desktop" and that "the player UI is ugly".

### 1.2 User preferences carried forward (HANDOFF)

- Windows only. Phone-only options are trimmed and useful ones kept. The startup warning is removed.
- Displays: 4K 32 inch now, 5K 39 inch later. Ctrl+wheel and Ctrl+plus/minus zoom already exist and are kept untouched.
- The player is video-first with compact, clear controls. The default quality is the highest obtainable.
- The NVIDIA enhancement entry stays simple (content, strength). WASAPI exclusive audio exists and is untouched.
- Default material is the original liquid glass. The result must be elegant and easy to use.
- Resource policy: one build worker, 4 GiB heap, no concurrent builds, heavy validation only with at least 8 GiB free physical memory and the sole Root build lease (`.coordination/resource-policy.json`, FACT). No participant dispatches cloud work. Root does, and `AGENTS.md` forbids paid cloud dispatch without authorization.

### 1.3 Diagnosis

1. Ordinary `VideoDetail` playback is not the Android overlay. It mounts the desktop-owned `DesktopWindowsVideoPhysicalLeaf` (`K/DesktopShell.kt`, branch `entryKey is BiliPaiNavKey.VideoDetail`, about :2086-2122; the leaf file is 1757 lines). That leaf is a stack: top strip, video, `DesktopWindowsVideoControlBar` below the video, and an optional right details panel. The vendored `VideoPlayerOverlay` is live only for Bangumi/PGC and the offline player. Whether the user's complaint was about the ordinary page or about Bangumi/offline is open (D1). The plan covers both and orders the work so that neither answer wastes the first release.
2. The "half phone" feel is mostly interaction idiom, not look: a 172 dp text-only rail; a 1280 dp centred feed cap that wastes 4K and 5K; an always-visible 48 dp three-dot button; no hover, right-click, hand cursor, tooltip or scrollbar on most pages; Material chips and switches (55 desktop source files mention `FilterChip`, material3 `Switch`, `AlertDialog`, `DropdownMenu` or `TabRow`; a coarse grep, FACT); a control bar glued below the video.

### 1.5 Scope

In scope: the shell (rail, shortcuts, window behaviour), Home density and card interactions, settings chrome, the ordinary video player, and a baseline for vendored pages.

**Players and pages that keep their current look in this program, stated plainly for the user:** Story, Live, audio mode, the offline player, and Bangumi/PGC (until the deferred V13), plus vendored detail pages (Dynamic, History, Favorites, Search results) apart from the baseline in section 3.8. The player dialogs (danmaku settings, share, coin, comment composer) keep their OS-titlebar 640 dp windows until the fast-follow slice W2.

**Non-goals, recorded so the gap is visible:** custom or undecorated title bar; OS Mica/Acrylic; boss key or any global hook; Q/W/E/R engagement keys; editing any vendored, pinned or hash-pinned file; the dormant original-VideoDetail route as a promised classic fallback; link/file drag-and-drop; single-instance forwarding; close-to-tray; taskbar jump lists and thumbnails. Each non-goal needs its own spec if the user wants it later.

### 3.5 Window behaviour [N + W]

- **Dynamic title (W6, fast-follow).** The title becomes `{video title} - BiliPai Windows` only while a video plays, so Alt-Tab and the taskbar say something useful. 16 test files contain the exact string `BiliPai Windows` (F16), and the earlier mapper counted about ten that locate the frame by it (REPORTED). - **Minimum size.** The minimum is 960 dp times zoom. At the 125% default that is 1200 px, pinned by `DesktopWindowsDisplayScaleTest` (REPORTED: 1200x850 at 150% DPI plus 125%). A 5K2K Windows third-snap at 150% is about 1137 px and does not fit. Decision D10 must be taken before S1. The default is to keep the pin.
- **Display facts.** All dp numbers assume Windows 150% on the 4K 32 inch and a 5120x2160 5K 39 inch. Both are unconfirmed (D2). The contract JSON labels those rows `assumed` and generates them from parameters, so a corrected scale is a one-line change.

### 3.6 Home [N proof, C compile, W look]

**Density rule.** Let Wc = W minus the rail footprint (through `LocalDesktopShellInsets`), C = Wc − 2·24, gutter 16, minCard 216 (a user card-width preset 160/200/260/320 is honoured, floor 160), maxCard 320.

- n = clamp(floor((C + 16) / (minCard + 16)), 2, nMax). nMax is 8 below Wc 2800 and 10 from 2800.
- card = (C − (n − 1)·16) / n. If card exceeds 320, cap the grid width at n·320 + (n − 1)·16 and centre it.
- A pinned column count and single-column mode delegate to the original function. The 1280 dp cap is dropped. Compact metadata turns off when the card is at least 200 dp wide.
- Properties (Python and JVM sweep W 960 to 4200): card within [216, 320]; Wc at least 884; columns non-decreasing in W within one rail presentation. The only allowed drops are at the rail switch points. I re-ran the sweep in a scratch script this pass: 0 violations.

### 4.2 Hosting and airspace rules [N rules, W proof]

1. Compose in the Main window can never draw over the heavyweight mpv Canvas. Overlay UI over video lives only in the existing transparent carrier (`DesktopCommandPopupWindow`: undecorated, transparent, non-focusable (F3), bounds equal to the anchor, `Window.shape` equal to the union of `desktopCommandHitRegion` rects; the bounds and shape behaviour is REPORTED, about `:213-264`) or in a focusable owned window (`DesktopFlyout`, `DesktopWindowsPlayerDialog`).
2. Visuals outside every registered hit region are clipped. The overlay therefore registers one full-surface region by reusing `DesktopOriginalPlayerInputLayer` (F7: `Box`, 1/255 alpha, `desktopCommandHitRegion`). Alpha 0 would be click-through on a layered window (F6).
3. The native slot is never enlarged, and letterboxing stays in Compose through `resolveVideoViewportLayout`, so carrier bounds equal the video rect (danmaku, subtitles, feedback and the seek preview all assume this).
4. **Snap rule (changed).** Chrome visibility, tier changes, panel open/close, cinema toggles and splitter drags never remount the native slot, and nothing animates its size. Each of those is one layout change, which means one `reportViewport` call. Only panel content alpha may animate. The splitter shows a ghost line and commits on release. A Python source check forbids any `animate*AsState` driving the size or weight of a `Row`/`Box` that contains the native slot. A fixture counts `reportViewport` calls per toggle (expected 1).
5. The carrier cannot take keyboard focus. Main owns the keyboard, the carrier owns the pointer over the video, and flyouts own their own window.
6. Every playback effect goes through the leaf's existing admitted lambdas (`command {}`, `current()`, `shell.playback.*`, `actions.*`). The overlay is callback-only. It never calls `MpvPlayer` or the assembly.
7. Any window that consumes the wheel keeps Ctrl+wheel zoom (section 6.4). Flyouts and dialogs keep using `DesktopWindowsOwnedDisplayScaleInputScope`, because they are focusable.
8. One `DesktopWindowKeyFallback` leaf slot and one root slot. No second `register()`, no global AWT hook. mpv native input stays at its three bindings and single owner, except under the contingency V0b (section 4.15).
9. **Gate (new).** The carrier overlay is built only after V0 shows a working delivery channel (section 11.1). Until then the DESKTOP layout is hypothesis, not plan.

### 4.3 Layout policy (pure) and corrected golden table [N]

Inputs: W, H (dp), video aspect (default 16/9), `panelOpen`, fullscreen, optional user panel width.

- `panelOpen` is one persisted tri-state. When the user never chose, the default is `W >= 1280`, evaluated **once at page entry**, never on resize (so a window drag does not flip the panel). Fullscreen never overwrites it.
- Panel docked: windowed when `panelOpen && W >= 640`. Fullscreen only when `panelOpen && W/H >= 2.0`.
- Panel width P = the user value clamped to 320..560, else `min(560, max(clamp(0.22·W, 340, 480), W − H·aspect))`, then `P <= W − 480`. If P is under 320 the panel is not docked.
- Stage = W − P. The video is the largest `aspect` rect in Stage x H, centred, with no outer padding.
- Tier by video width: L at least 960, M 640 to 959, S under 640. The dock capsule width is `min(1280, videoW − 32)`.

| Case (W x H dp) | Mode | Panel | Video rect | Tier | Bars |
|---|---|---|---|---|---|
| 960 x 680 (minimum) | default, panel closed (W under 1280) | 0 | 960 x 540 | L | 70 top and bottom |
| 960 x 680 | panel opened by the user | 340 | 620 x 349 | S | 166 top and bottom |
| 1088 x 720 | default, panel closed | 0 | 1088 x 612 | L | 54 top and bottom |
| 1088 x 720 | panel opened by the user | 340 | 748 x 421 | M | 150 top and bottom |
| 1280 x 690 (narrow window example) | default | 340 | 940 x 529 | M | 81 top and bottom |
| 2048 x 1101 (4K32, Win150 x 125%) | default | 451 | 1597 x 899 | L | 101 top and bottom |
| 2048 x 1101 | cinema | 0 | 1957 x 1101 | L | 45 left and right |

| 2731 x 1101 (5K2K, assumed) | default | 560 | 1957 x 1101 | L | 107 left and right |

The draft's two rows at 960 and 1088 assumed the panel open by default, which contradicts the rule above. Both cases are now listed. Height, not width, binds on ultrawide. Extra width goes to the panel first, then to margins. A 1565 dp seek rail on a one-hour video is about 2.3 s per dp (3600/1565, recomputed), so arrows, wheel and fine-scrub are the precision tools.

### 6.3 Click state machine (changed) [N]

The draft delayed every pause by `clamp(multiClickInterval, 180, 300)` ms. That adds latency to every pause, and a user whose Windows double-click time is the 500 ms default would get two pauses and no fullscreen. The replacement has no latency.

- Press 1 toggles play/pause immediately and records (time, position, previous state).
- A second press within the unclamped `awt.multiClickInterval` and within 6 dp **undoes** the toggle (restoring the recorded state) and enters fullscreen. Otherwise the record is cleared.
- The centre OSD flash is delayed by `min(multiClickInterval, 250 ms)`, so a double-click does not flash twice.
- Cost, stated honestly: a double-click produces a pause-then-resume of a few milliseconds (YouTube behaves the same way). If the user dislikes it, the alternatives are in D3.
- The state machine is pure and takes an injected clock. The golden test covers single, double within and outside the interval, a press while a flyout is open, and a press while Main is inactive.

## 9. Slices, order and cost

### 9.1 Rules

- A compile (L2) after **every** slice, never only per batch. A slice is capped at about 600 changed lines. Anything larger is split.
- The first cloud run is the API-probe unit XP (a throwaway compile unit that references every uncertain symbol), so API errors surface before dependents are written. Dispatch is Root's decision and is subject to the resource policy and D14.
- The leaf is serialised: slice owners write leaf hunks as patch files against anchors, and Root lands them as one integration commit per release.
- Costs are engineer-days of blind Kotlin, excluding cloud wait and compile-fix loops. They are not calendar time.

## 11. Real-window-only proofs [W]

### 11.1 V0, the input-delivery probe (first player gate)

V0 is a validation-property-gated probe. It re-runs the exact scenario that failed on 2026-10-15 (F6) on the ordinary-video leaf.

**Arms.**

- **Arm A:** a full-surface 1/255 region in the existing carrier (F7), with the real chrome children.
- **Arm B:** the same region with no children, to separate an alpha or region problem from a child-capture problem.
- **Arm C:** the leaf's existing native-surface AWT listeners (F8), as the baseline expected to fail (F4).

**What is counted, in windowed and fullscreen, while Main is active and while it is not:** primary press, secondary press, double-click, wheel, Ctrl+wheel, Back button, and hover and move.

**Recorded-failure repro:** let the chrome auto-hide, click the video centre, and see whether the controls come back; then click to pause.

**Keyboard matrix:** arrows, Shift and Ctrl arrows, J, L, M, F, digits, comma, period and Alt+Enter, each checked after a carrier click, after a native Canvas click, after a flyout closes, and after Alt-Tab. Two focus variants: the Compose viewport only, and the viewport plus the native surface.

**Budget (proposals, to be confirmed after the first measurement, D18):**

- Idle-hidden overhead against LEGACY at the same 4K video: at most 1% GPU and at most 1% of one CPU core.
- Memory delta at most 64 MB. A 4K layered window backing store is about 33 MB (3840 x 2160 x 4 bytes, an arithmetic inference), so 64 MB is the proposed cap.
- Dock-visible overhead is measured and recorded for the user. No cap is proposed before a first number exists.

**Pass criteria and decision tree.**

| Result | Consequence |
|---|---|
| Arm A delivers every event type in every case, reveal-by-click after auto-hide works, the Back button arrives, and the keyboard matrix delivers every router key | Proceed to V3 to V5. |
| Arm A fails but Arm B passes | A child-capture or composition problem. Adjust the overlay structure and re-run. |
| Arms A and B fail | V0b: extend the mpv native bindings (4.15). V3 to V8 stay blocked until one channel passes. |
| Neither channel passes | The overlay stays LEGACY. R1 and R2 still deliver. The player complaint is answered by V2b, V6 and X3. |
| Budget missed | `player_layout` is not flipped. |

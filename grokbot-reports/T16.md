## 问题 2：确认类对话框怎么开窗？目前是几个窗口？

### `DesktopWindowsPopupMaterial.kt`

- `DesktopWindowsPopupMaterialHost`（`:61`）：**不开窗**，只在已有窗口里挂玻璃/壁纸背景。
- `DesktopWindowsPopupDialog`（`:84-98`）：缓存确认体的平台口。开窗路径：

```
DesktopWindowsPopupDialog
  → DesktopWindowsPlayerDialog("清理缓存", preferredHeightDp = 600)
    → DialogWindow.create
      → ComposeDialog(owner, DOCUMENT_MODAL)   // 一个带 OS 标题栏的 owned 对话框
```

内容外包一层 `DesktopDetailWindow` + 居中 `Box`。确认/取消回调仍在上游 cache 逻辑里。相对 Main：**+1 个窗口**。

### `DesktopCommandPopupWindow.kt`

**不是确认对话框。** 它是视频上的透明、无装饰、不可聚焦 carrier（`ComposeDialog(MODELESS)` + `isUndecorated = true`，约 `:185-193`），给命令条/品牌回执用。与 W2 的“确认对话框”不是同一条路径。

### 取消关注确认（设计点名的确认场景）

```
rememberFollowActionWithConfirmation（上游，生成代码把 AppAlertDialog 绑到）
  → DesktopWindowsFollowConfirmationDialog
       ├─ Main 正在显示：DesktopWindowsPlayerDialog("取消关注", height=300)
       │    → DialogWindow → ComposeDialog(DOCUMENT_MODAL)   // +1 窗口
       │    → 内容里再画 AppAlertDialog（同一窗口内的 Compose，不是第二窗）
       └─ 无 Main：直接 AppAlertDialog（通常落在当前 Compose 树；无额外 AWT 窗）
```

因此：一次“取消关注”确认在 Main 上 = **1 个额外 owned 对话框**（不是 2 个 AWT 窗）。但若用户**已经**在另一个 `DesktopWindowsPlayerDialog` 里（例如 `DesktopWindowsVideoEngagementSection.kt:236`「设置关注分组」），再点取消关注，会再开一个 PlayerDialog → **叠两个 owned 对话框**。这更像“单窗口确认”要消掉的路径。

同类“确认内容包进新 PlayerDialog”的还有：`DesktopHotDanmakuAlertDialog`（`:53`）、`DesktopWindowsCommentAlertDialog`（`:81`）。

## 问题 3：单窗口确认的最小改动（≤3 个文件）

建议三文件（与设计第 608 行点名的两个文件对齐，再加 Follow 确认）：

1. **`DesktopWindowsDanmakuDialog.kt`** — 给 `DesktopWindowsPlayerDialog` 增加 `preferredWidthDp: Int = 640`，并传给 `desktopWindowsPlayerDialogInitialBounds`（宽度透传；默认行为不变）。
2. **`DesktopWindowsFollowConfirmationDialog.kt`** — 若 `LocalAwtWindow.current is ComposeDialog`（已在某个 owned 对话框内），只渲染 `AppAlertDialog`，不再套一层 `DesktopWindowsPlayerDialog`；否则保持现逻辑（Main 上仍开 owned 窗，避免被 MPV 盖住）。
3. **`DesktopWindowsPopupMaterial.kt`** — `DesktopWindowsPopupDialog` 在透传落地后显式传一个更窄的 `preferredWidthDp`（提案草稿用 480，**待 Root 定数值**）；可选：同样加“已在 ComposeDialog 内则不再开窗”的守卫（若缓存确认只从设置页触发、且设置页不在 PlayerDialog 内，这条可能用不上——**不确定**，需 Root 确认缓存确认的调用栈是否会嵌套）。

不改：`DesktopCommandPopupWindow.kt`（carrier，与确认无关）、`build.gradle.kts`、受保护路径。

几何测试（`DesktopWindowsPlayerDialogGeometryTest`）建议另开提交加一条 `preferredWidthDp` 用例；本提案为压在 3 文件内，测试列为 Root 可选第 4 项。

## 问题 4：第 67 行非目标 vs 第 707 行 “without OS title bars”

| 出处 | 原文要点 |
|---|---|
| **§1.5 第 65 行** | 玩家对话框在 W2 之前保持 **OS-titlebar 640 dp** 窗口 |
| **§1.5 第 67 行非目标** | **custom or undecorated title bar** 明确不在本程序范围 |
| **§8.1 第 608 行** | W2 文件：`PopupMaterial.kt`、`DanmakuDialog.kt`；工作：**preferredWidthDp pass-through and a one-window confirm dialog** |
| **§9.2 第 685 行** | W2：**Native dialog width pass-through and one-window confirm dialog** |
| **§9.3 第 707 行 Fast-follow 一句话** | “… **native dialogs without OS title bars**, a dynamic window title” |

**判断（更像设计意图）：第 67 / 608 / 685 行。** W2 是「宽度可传 + 确认不叠窗」，**不是**去掉 OS 标题栏。依据：

1. 非目标用词强硬（“recorded so the gap is visible”），把 undecorated title bar 整项排除。
2. W2 的精确描述（608、685）只提 width pass-through 与 one-window confirm，未提 undecorated / 去标题栏。
3. 第 65 行把“OS-titlebar 640 dp”绑在 W2 之前；结合 608，W2 改的是 **640（宽度）** 和确认窗数量，不是标题栏形态。
4. 第 707 行是整包 Fast-follow 的用户可见摘要，把多个切片揉成一句；同段还有 H4/H3/V7/V8/W6，**“without OS title bars”更像笔误或与已 undecorated 的 `DesktopCommandPopupWindow` carrier 混淆**（该 carrier 本来就无装饰，且不是 W2 文件）。

**不确定：**

- 作者是否曾想过 W2 顺带把 PlayerDialog 改成无标题栏（与第 67 行冲突，若要做必须先改非目标）。
- “one-window confirm”是仅指 Follow 嵌套场景，还是也要求 Main 上的确认改用 carrier/无标题栏窗（那样会撞非目标）。
- 第 65 行 “until W2” 是否被误读成“W2 之后不再有 OS 标题栏”——字面可两解；我按 608/685/67 取“保留标题栏、修宽度与叠窗”。

**需要 Root 书面确认：** W2 是否 **禁止** 改 `ComposeDialog` 的装饰/标题栏；宽度默认是否仍 640；确认“单窗口”是否仅防嵌套。

背景：任务 6 的 6c 把 6 项失败判为产品缺陷（BAS 弹幕发布 4 项、早期视频详情 2 项），当时只写了补丁。Root 的决定：两项都按“产品应当符合测试描述的行为”处理，要真正修好并在 Linux 上验证，但只放在隔离分支，不进主线，等 Root 审。

## T8a BAS 弹幕发布（分支 grokbot/fix-bas-publication）
现象：过期的 BAS 弹幕只在画面“能渲染”时才被清理，窗口隐藏后旧计数一直挂着；上游的相关开关只管绘制，不管清理。
做法：
1. 确认补丁（你已写好的那份）能应用，再确认它能让 DesktopBasOverlayPublicationTest 的 4 项通过，且不破坏 danmaku 包的其它 26 个测试类（全部跑一遍）。
2. 对照固定上游（desktop/upstream-slices 里的 v038 帧节奏相关文件）说明：桌面端这里的清理时机偏离了上游哪一行、为什么。偏离必须是桌面端有意的适配；否则以上游为准。
3. 评估隐藏窗口、恢复显示、快速切换视频三种场景下补丁是否会漏发布或重复发布（用已有测试替身写出这三个场景的新测试）。
4. 报告：补丁、测试结果、风险。

## T8b 早期视频详情（分支 grokbot/fix-early-video-detail）
现象：DesktopWindowsEarlyVideoDetailTest 两项失败：播放地址失败时，没有等到详情回调就报了错误。仓库里写明过一条桌面端规则“播放地址失败时要等详情回调之后再报错”，后来生成器不再套用它，规则本身也没被撤回；上一份补丁里要匹配的那行已经找不到。
做法：
1. 找出这条规则的文档位置（PARITY.md、WINDOWS.md 或测试注释）和引入、失效的提交，写进报告。
2. 按生成器当前的实际形态重写这条适配：在对应生成器里用带证明（inverse proof）的方式重新套用，加或更新 Python 测试证明锚点存在、适配被应用、逆向可还原；不能靠修改测试来让它通过。
3. 跑 DesktopWindowsEarlyVideoDetailTest 全部用例、早期详情相关的其它测试类、受影响生成器的 Python 测试；重新 compileKotlin/compileTestKotlin。
4. 报告：规则是否仍然成立（若文档与上游明确冲突，写出冲突，不要自行裁决）、补丁、测试结果。
